## 一、核心架构：基于宪法准则的头部固定

### 1.1 头部区域的不可压缩性

**宪法准则和操作禁止永远在头部区域，永不离开 head buffer。**

```
head_buffer 内容：
┌────────────────────────────────────────────┐
│ 宪法准则（Constitutional Rules）            │ ← 永不压缩
│ 操作禁止（Operational Prohibitions）        │ ← 永不压缩
│ Master Agent 初始目标 / session scope       │ ← 永不压缩
│ 首条用户任务声明（~1500 tokens pinning）    │ ← 永不压缩
│ 系统提示 / skill_zone                      │ ← 永不压缩（享受 prefix cache）
└────────────────────────────────────────────┘
```

### 1.2 工具内容的压缩上限

| 类型 | 压缩上限 | 理由 |
|------|---------|------|
| tool result | **L3 掩码**，不得进入 L4 丢弃 | 工具输出是"事实数据"，模型无法自行生成 |
| tool call | **可 L4 丢弃** | 调用意图已由推理链覆盖，请求体只是推理的函数参数翻译 |
| 推理链 | 可 L4 丢弃 | 模型推理可重新生成 |
| 失败尝试 | 可 L4 丢弃 | 失败记录已被后续推理覆盖 |
| 废弃规划 | 可 L4 丢弃 | 规划已废弃 |

#### L3 掩码格式规范（v5 明确）

掩码由**工具生成的结构体 + LLM 拼接的意图总结**两部分组合。一次 tool_call 记录为一个 step，`step_id` 是全系统统一标识符。

```
[掩码段 step_42 | 原 8.2K | grep | pattern:"redis.*timeout"]
  ├─ 结构体部分（框架从 tool call/result 中自动提取）
  │     step_id, 原大小, 工具名, 关键参数(pattern/path/等)
  └─ 意图总结（LLM 在压缩时拼接的语义说明）
        "搜索 redis timeout 相关行"
```

框架负责提取结构化的工具参数（pattern、path、文件名等），LLM 负责生成语义层面的意图总结。两者组合保证掩码既有精确的展开索引又有可理解的上下文。

#### L3 掩码的二级合并

当累计 L3 掩码条目超过阈值（默认 100 条）时，对相邻同类型 block 合并：

```
[掩码段 step_42-step_55 | 原 105K | 14×grep | patterns:"redis.*timeout", "connection.*refused", ...]
```

合并仅对同类型（read-only / side-effecting）、同主题（连续 step 且相关文件重叠）的 block 生效。

### 1.3 工具输出量的软上限（v5 修正）

```
默认上限：max_tool_output = 32KB（可配置）

正常情况：工具输出 ≤ 32K → 完整保留，不做 snip
超出场景：
  - 说明输出了异常量级的内容，不能直接把 32K+ 原文导入 session
  - 启用特化 agent 模式：无截断保留完整返回，但存储到专用存储位置
  - session 中只挂占位符或引用地址（例如 "[大型输出 ref: step_42_full_output] 原始输出已归档"）
  - 主 LLM 需要时通过引用地址按需加载（context_expand 或类似机制）

特殊子 agent 例外：
  - 等幂查询类可启用无截断模式，所有原文记录到 L0 jsonl（完整保留）
```

### 1.4 Session 树形结构与 refs.jsonl 的关系（v5 明确，v6 修正）

> **v6 修正**：step 之间是线性递增关系，不存在 `parent_step_id`。树形拓扑在 **session 级别**——session list 和派生 session list 之间有 fork 关系。step_id 是全局递增序号，可以跳步（被压缩/丢弃后序号跳过），但 step 之间没有情缘关系。

树形段拼装模型（见[树形段拼装模型-规格定义](树形段拼装模型-规格定义.md)）中的子 agent fork 操作，在 session 级别表达：

核心原则：
- **step 是线性的** — step_id 全局递增，按序拼接即可，无父子关系
- **session 才有 fork** — 主 session 派生出子 session 时，子 session 记录继承来源（从哪个 session 的哪个 step 开始 fork）
- **Session 树** — 主 session 可以 fork 出多个子 session，形成 session 级别的树形拓扑
- **上下文拼接** — 沿 session fork 链收集各 session 的 step 序列，按 step_id 升序拼接
- **折叠与展开** — 压缩（折叠）对应 compress.jsonl 中 level 升级；context_expand（展开）对应从 L0 jsonl + compress.jsonl 中恢复原文渲染
- **L0 jsonl** 是物理存储（append-only 线性序列），**refs.jsonl** 是引用追踪（热度 + 属性），**session 元数据**记录 fork 拓扑

**有序恢复**：直接按 step_id 升序加载，无需回溯。跳步 = 某些 step 被压缩/丢弃后序号不连续，属正常现象。

## 二、存储结构：三件套 + 分表模式

### 2.1 核心存储三件套（v5 明确优先级）

```
优先级 1: {uuid}.jsonl                 # L0 主文件（append-only，带 step 标记，只允许自增）
优先级 2: {uuid}.refs.jsonl            # list[dict{stepid: 引用次数}] — 引用追踪
优先级 3: {uuid}.compress.jsonl        # 压缩等级元数据
```

**有这三个文件，按顺序做过什么逻辑上都可以还原。** 不需要 DB 事务语义——文件级 append + 原子 rename 足够。

**L0 jsonl 格式**：

```jsonl
{"step_id":1,"type":"user","token_count":85,"content":"帮我把 Redis 配置从 config.py 迁移到独立的 redis_config.py"}
{"step_id":2,"type":"reasoning","token_count":320,"content":"需要先定位 Redis 相关配置在哪些文件中..."}
{"step_id":3,"type":"tool","token_count":1247,"content":"[call] grep(pattern=redis, path=./)\n[result] config.py:12: REDIS_HOST=localhost"}
```

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `step_id` | int | 全局递增序号，全系统统一标识符 |
| `type` | string | `user` / `reasoning` / `tool` / `plan` / `failed` |
| `token_count` | int | 框架写入时 tokenizer 预计算，用于 decay 追踪和折叠管理 |
| `content` | string | 该 step 的完整原文。`type=tool` 时 `[call]` 和 `[result]` 合并在同一步内（一次往返 = 一个 step） |

**压缩规则**：`type=tool` 时 `[call]` 段可 L4 丢弃（推理链已覆盖意图），`[result]` 段 L3 封顶。其余类型按 §4.4 阈值判定。

### 2.2 compress.jsonl 格式规范（v5 定型）

```jsonl
// level 取值范围：0-3。L4 丢弃的内容不出现在此文件中。
// step_id 是全系统统一标识符（一次 tool_call = 一个 step）

{"step_id":1,"level":0,"content_hash":"sha256:aaa","compressed_at_step":null,"compressed_at_header_version":null}
{"step_id":3,"level":2,"content_hash":"sha256:ccc","compressed_at_step":8,"compressed_at_header_version":"h_v1"}
{"step_id":4,"level":3,"content_hash":"sha256:ddd","compressed_at_step":12,"compressed_at_header_version":"h_v1"}
```

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `step_id` | int | 与 L0 jsonl 和 refs.jsonl 中的 step_id 同源 |
| `level` | int (0-3) | 当前压缩级别（折叠等级）。L4 丢弃的 step 直接从此文件删除行 |
| `content_hash` | string | 当前级别内容的 SHA256 hash |
| `compressed_at_step` | int\|null | 压缩发生的 step 编号 |
| `compressed_at_header_version` | string\|null | 压缩时 head_buffer 版本号。replay 时若与当前版本不同标记为 stale |

**L4 丢弃**：从 compress.jsonl 中**删除对应行**。删除 = block 不再出现在任何材料化视图中。全局压缩时 LLM 可通过跳号删除不重要 step。

**版本链长度**：5000 轮上限（当前 Trae 用户触发只有 50 轮）。

### 2.3 压缩等级内容语义（v5 明确）

| 级别 | 内容 | 说明 |
|------|------|------|
| L1 | 初级压缩（去噪瘦身） | 去掉冗余格式、重复日志行、空白等噪声 |
| L2 | 事实保留 | 保留关键事实（路径、配置值、错误消息），丢掉过渡性推理 |
| L3 | 纯掩码 | 只留「做了什么任务」+ token 量，具体内容需结合上下文理解 |

具体文件格式（字段、结构）在压缩脚本框架中实测定型。

### 2.4 refs.jsonl 格式（v5 新增，v6 扩展归档与高级属性）

#### 2.4.1 基础格式

```jsonl
// 每条记录对应一个 step 的引用追踪和属性，step_id 全局递增（可跳步）
{"step_id":42,"ref_count":1,"last_ref_at_step":67,"created_at_header_version":"h_v1","strength":1.1,"task_group_id":1,"task_boundary":false}
{"step_id":55,"ref_count":3,"last_ref_at_step":89,"created_at_header_version":"h_v1","strength":1.3,"task_group_id":1,"task_boundary":false}
{"step_id":58,"ref_count":0,"last_ref_at_step":null,"created_at_header_version":"h_v2","strength":1.0,"task_group_id":2,"task_boundary":true}
{"step_id":60,"ref_count":0,"last_ref_at_step":null,"created_at_header_version":"h_v2","strength":1.0,"task_group_id":2,"task_boundary":false}
```

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `step_id` | int | step 编号（全局递增，可跳步） |
| `ref_count` | int | 被后续 step 引用的累计次数（热度信号） |
| `last_ref_at_step` | int\|null | 最后一次被引用的 step 编号 |
| `created_at_header_version` | string | 该 step 创建时的 head buffer 版本号。replay 时若与当前 header 版本不匹配标记为 stale |
| `strength` | float | 累积访问强度（借鉴 Knox-MS 间隔重复），调制 decay 速率。每次被引用 +0.1（β 因子） |
| `task_group_id` | int | 所属任务组编号。默认每 50 步自动划分一个 task_group（可配置） |
| `task_boundary` | bool | 是否为新 task_group 的起点。用于压缩策略差异化处理 |

> **v6 修正**：移除 v5 中的 `parent_step_id` 和 `sub_agent_forked_from`。step 之间是线性关系，不存在父子情缘。Session 级别的 fork 关系记录在 session 元数据中，不在 refs.jsonl 中。

**写入时机**：首次任务意图审定、header v1 确立后开始记录（计划模式阶段不记录）。header 版本演进（v1→v2→v3）通过 `created_at_header_version` 追溯，版本号定义在 head buffer 前端。

作用：
- LLM 全局 summary 时备份历史版本 → 作为 checkpoint
- 按 step_id 计数 = 记录 step 活跃度，避免折叠对应 step
- `strength` 实现"越用越牢固"的正反馈（借鉴 Knox-MS 时频双因子）
- `task_group_id` + `task_boundary` 支持任务级压缩策略差异化
- 未按顺序引用到的 step = 软删除，异常恢复时不加载

#### 2.4.2 有序恢复（进度丢失重建）

step_id 是全局递增的线性序号，恢复时直接按 step_id 升序加载即可：

```
恢复算法：
  1. 读取 refs.jsonl 中所有 step_id
  2. 按 step_id 升序排序
  3. 从 L0 jsonl 按序加载这些 step 的原文 → 拼接上下文
```

跳步是正常现象——某些 step 被压缩/丢弃后，step_id 序号不连续（如 42, 55, 58, 60），恢复时仍按升序拼接。

恢复场景是低频操作（仅在进度丢失时），O(n log n) 排序开销可接受。

#### 2.4.3 task_group 归档与跳步机制（v6 新增）

以 50 步为一个 task_group（默认值，可配置）。task_group 是上下文自省式管理的天然节点。

**归档触发**：当一个 task_group 内的所有 step 均已压缩至 L3 或 L4，且 ref_count=0（无活跃引用），该 task_group 可归档。

**归档流程**：

```
  1. 将 step 1-50 的 refs.jsonl 条目连续复制到归档文件：
     {uuid}.refs.archive.{task_group_id}.jsonl
  
  2. 从活跃 refs.jsonl 中移除这些条目（跳步）
     → 活跃 refs.jsonl 现在只包含 step 51+ 的条目
  
  3. 归档文件保留完整属性（ref_count, strength, task_group_id 等）
     → 需要时可从归档文件恢复（反向操作：复制回活跃 refs.jsonl）
```

**跳步示例**：

```
归档前 refs.jsonl（活跃）：
  step_1, step_2, ..., step_50, step_51, ..., step_60

归档后 refs.jsonl（活跃）：
  step_51, step_52, ..., step_60

归档文件 refs.archive.1.jsonl：
  step_1, step_2, ..., step_50（连续完整保留）
```

**归档文件的存储位置**：与三件套同目录，命名规则 `{uuid}.refs.archive.{task_group_id}.jsonl`。归档文件不参与常规压缩判定，仅在 context_expand 或恢复时按需加载。

**跨 task_group 引用保护**：若 step N（task_group=1）被 step M（task_group=2）引用，则 task_group=1 的归档被阻止，直到 step N 的 ref_count 归零或引用方也被归档。

#### 2.4.4 高级判断属性扩展清单

refs.jsonl 的 step_id 条目可按需扩展更多属性，以下为候选清单（按需启用）：

| 属性 | 类型 | 用途 | 来源 |
|------|------|------|------|
| `strength` | float | 累积访问强度，调制 decay 速率 | 每次引用 +0.1 |
| `task_group_id` | int | 所属任务组标识 | 框架按 50 步自动划分或 LLM 标记 |
| `task_boundary` | bool | 是否为新任务的起点 | LLM 标记或框架检测 |
| `semantic_hold` | bool | 语义安全网标记（暂缓压缩） | Redis 召回判定（§2.5） |
| `compaction_depth` | int | 被压缩的次数 | 每次升级 level 时 +1 |
| `related_files` | list[string] | 关联文件路径 | 框架从 tool call 中提取 |

### 2.5 Redis 缓存层 RAG 召回（v6 新增）

> 借鉴 Knox-MS 多策略检索思想，为 context_search 工具（§12.2）提供持久化索引后端，同时反哺压缩决策。Redis 作为**热数据缓存层**，L0 jsonl 仍为冷存储和恢复源。

#### 2.5.1 Redis 数据结构

```
┌─────────────────────────────────────────────────────┐
│                    Redis 存储层                       │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Hash:   ctx:{session_id}:steps                     │
│          field = step_id                            │
│          value = JSON{type, token_count, text,      │
│                       embedding, created_at}        │
│                                                     │
│  ZSet:   ctx:{session_id}:timeline                  │
│          score = step_id（天然有序）                  │
│          member = step_id                           │
│                                                     │
│  ZSet:   ctx:{session_id}:recency                   │
│          score = unix_timestamp(last_accessed)      │
│          member = step_id                           │
│                                                     │
│  Hash:   ctx:{session_id}:meta                      │
│          field = step_id                            │
│          value = JSON{ref_count, strength,          │
│                       related_files, task_group_id} │
│                                                     │
│  Vector: ctx:{session_id}:vss                       │
│          (Redis Search 的 Vector Index)             │
│          field = embedding, dim = 768/1536          │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 2.5.2 数据写入时机

```
每步 LLM 输出后（框架侧，非阻塞）：

  1. HSET ctx:{sid}:steps {step_id} {step_json}
     → 存 step 元数据 + 原文摘要（前 500 字符）
  
  2. ZADD ctx:{sid}:timeline {step_id} {step_id}
     → 维护有序时间线
  
  3. ZADD ctx:{sid}:recency {now_ts} {step_id}
     → 维护时效性索引
  
  4. 异步任务（不阻塞主流程）：
     → 调 embedding 模型 → 得到向量
     → HSET 更新 embedding 字段
     → Vector Index 自动同步
```

**关键**：embedding 计算异步执行。主流程只写 step_json + timeline，毫秒级。向量索引在后台补全，不影响响应速度。

#### 2.5.3 三路融合召回（context_search 的 Redis 实现）

升级 v5 §12.2 的 BM25 现建索引为三路融合召回：

```python
def context_search_redis(session_id, query, limit=8):
    """三路融合召回 — 基于 Redis"""
    
    # ── 路 1：向量语义召回（Redis Search VSS）──
    query_embedding = embed(query)  # 768/1536 维
    semantic_hits = redis.ft(f"ctx:{session_id}:vss").search(
        Query(f"*=>[KNN {limit} @embedding $vec as score]")
            .sort_by("score")
            .return_fields("step_id", "score"),
        query_params={"vec": query_embedding}
    )
    # → [{step_id, score}]  语义相似度 top-K
    
    # ── 路 2：关键词召回（Redis Search 全文索引）──
    keyword_hits = redis.ft(f"ctx:{session_id}:steps").search(
        Query(tokenize(query)).sort_by("_score").limit(0, limit)
    )
    # → [{step_id, score}]  BM25 分数 top-K
    
    # ── 路 3：时效性召回（ZSet 范围查询）──
    recent_hits = redis.zrevrange(
        f"ctx:{session_id}:recency", 0, limit - 1, withscores=True
    )
    # → [(step_id, timestamp)]  最近访问的 step
    
    # ── 融合打分 ──
    candidates = {}
    for h in semantic_hits:
        candidates[h.step_id] = {"semantic": h.score}
    for h in keyword_hits:
        candidates.setdefault(h.id, {})["keyword"] = h.score
    for step_id, ts in recent_hits:
        candidates.setdefault(step_id, {})["recency"] = ts
    
    scored = []
    for step_id, scores in candidates.items():
        s_sem = scores.get("semantic", 0)    # 归一化到 [0,1]
        s_key = scores.get("keyword", 0)     # 归一化到 [0,1]
        s_rec = scores.get("recency", 0)     # 归一化到 [0,1]
        
        # 可量化权重（默认值，可调）
        final = 0.50 * s_sem + 0.30 * s_key + 0.20 * s_rec
        scored.append((step_id, final))
    
    scored.sort(key=lambda x: x[1], reverse=True)
    return [step_id for step_id, _ in scored[:limit]]
```

#### 2.5.4 可量化指标

| 指标 | 公式 | 默认值 | 说明 |
|------|------|--------|------|
| 语义权重 $w_{sem}$ | 配置项 | 0.50 | 向量相似度占比 |
| 关键词权重 $w_{key}$ | 配置项 | 0.30 | BM25 分数占比 |
| 时效性权重 $w_{rec}$ | 配置项 | 0.20 | 最近访问占比 |
| 召回阈值 $\theta$ | final score ≥ θ 才返回 | 0.35 | 低于此分数的不返回 |
| 向量维度 | embedding 模型决定 | 768 (bge-m3) 或 1536 (text-embedding-3-small) | |
| KNN 候选数 | 每路返回 top-K | 8 | 融合前每路的候选量 |

**归一化方法**：
- 语义分数：余弦相似度，天然 [0,1]
- BM25 分数：`score / max_score_in_batch`（批次内归一化）
- 时效性分数：$e^{-0.01 \times (now - last\_accessed\_seconds)}$（指数衰减到 [0,1]）

#### 2.5.5 与压缩流程的衔接

Redis 不仅服务于 context_search 工具，还反哺压缩决策：

```
压缩判定流程（改造 §5.2 Step 2）：

  当 step 的 effective_decay 进入模糊地带（阈值 80%-120%）：
    1. 查 Redis：context_search_redis(session_id, step.text, limit=3)
    2. 若返回的 top-1 score > 0.6 → 该 step 与近期上下文高度相关
       → 暂缓压缩，标记 semantic_hold=true
    3. 若 score < 0.35（低于召回阈值）→ 正常压缩
    4. 中间地带 → 按原规则压缩
```

#### 2.5.6 Redis vs 当前 v5 设计对比

| 维度 | v5 当前（BM25 现建索引） | Redis 方案 |
|------|------------------------|-----------|
| 语义召回 | 无 | VSS 向量索引 |
| 关键词召回 | BM25 现扫 L0 jsonl | Redis Search 全文索引（持久化） |
| 时效性召回 | refs.jsonl 的 last_ref_at_step | ZSet 精确时间戳 |
| 查询延迟 | O(n) 扫文件，百 ms 级 | O(log n) 索引查询，个位数 ms |
| 额外依赖 | 无 | Redis Stack（含 Search + VSS） |
| 数据持久化 | 文件系统（L0 jsonl） | Redis AOF/RDB + L0 jsonl 双写 |
| 故障恢复 | 无需恢复 | Redis 挂了 → 从 L0 jsonl 重建索引 |

#### 2.5.7 存储三件套扩展（v6）

引入 Redis 后，存储从三件套扩展为**三件套 + Redis 缓存层**：

```
优先级 1: {uuid}.jsonl                 # L0 主文件（append-only，冷存储，恢复源）
优先级 2: {uuid}.refs.jsonl            # 引用追踪（活跃路径）
优先级 3: {uuid}.compress.jsonl        # 压缩等级元数据
优先级 4: Redis ctx:{session_id}:*     # 热数据缓存层（可重建）
```

Redis 是**可丢弃的缓存层**——所有数据均可从 L0 jsonl + refs.jsonl 重建。Redis 故障不影响数据完整性，只影响检索性能。

## 四、触发阈值：引用距离驱动的压缩等级判定（v5 简化）

### 4.1 ContentBlock 模型（v5 简化，移除 heat_score）

```python
class ContentBlock:
    step_id: int
    step_type: str                # user / reasoning / tool / plan / failed
    token_count: int              # 从 L0 jsonl 加载
    content: str                  # 完整原文
    segments: list[Segment] | None  # type=tool 时解析 [call]/[result]；其他类型为 None
    created_at_step: int
    last_referenced_at_step: int
    reference_count: int          # 热度信号（refs.jsonl 的 ref_count）
    strength: float               # 累积访问强度（v6 新增，借鉴 Knox-MS 间隔重复）
    expand_count: int
    task_id: str | None
    task_group_id: int            # 所属任务组（v6 新增，默认每 50 步一组）
    related_files: Set[str]

class Segment:
    kind: str                     # "call" | "result" | "full"
    text: str
    max_compression_level: int    # call=4（可丢弃），result=3（不可丢弃），full=4
```

**加载逻辑**：从 L0 jsonl 读取 → `step_type=type`，`token_count=token_count`。若 `step_type=tool`，解析 `content` 中 `[call]` / `[result]` 标记生成两个 `Segment`，各自携带 `max_compression_level`。非 tool 类型 `segments=None`，压缩时整步统一处理。

### 4.2 引用追踪策略

引用追踪的规范来源是 `refs.jsonl`（§2.4），其 `ref_count` + `last_ref_at_step` + `strength` 三个字段覆盖所有追踪需求。

**标记注入与回写机制**：

```
框架侧注入：
  拼接上下文时，每个 step 的内容前自动插入 [step_N] 标记
  → LLM 看到的上下文自然包含这些标记

LLM 侧引用：
  模型输出中提及 "根据 [step_42] 的 grep 结果..." 即计为引用
  框架对每步 LLM 输出做正则解析，匹配 \[step_\d+\] 模式

框架侧回写：
  每步 LLM 输出后，解析出的 step_id 列表 → 更新 refs.jsonl 中对应 ref_count
  ref_count 增量 +1，last_ref_at_step 更新为当前步号
```

**追踪粒度**：per-step（引用计数）与 per-step（decay 追踪）解耦。per-step 指的是每步结束后立即更新 decay 计数器和 ref_count（纯算术，低开销）；压缩执行（调 3B 模型、写 compress.jsonl）在批次边界或水位阈值时触发。

三种检测机制各司其职：

| 机制 | 精度 | 适用对象 | 角色 |
|------|------|---------|------|
| **框架层注入 + 回写** | 精确 | tool call / tool result | 主方案：LLM 输出中出现 `step_42` 标记（如 "根据 step_42 的 grep 结果..."）即计为引用，回写到 refs.jsonl 的 ref_count |
| **Token 重叠启发式** | 近似 | 所有 block | 辅助热度信号，补充未被显式标记的隐式引用 |
| **BM25 (context_search)** | 精确关键词 | context_expand 后端 | 被动查证工具，LLM 主动调用，不计入 ref_count |

### 4.3 有效衰减公式（v5 简化，v6 增加 strength 调制）

```
raw_decay = 自上次被引用后，后续各步产生的 token 总量
           = Σ token_count（从 last_referenced_at_step+1 到当前步，基于 L0 jsonl 字段）
effective_decay = raw_decay × reference_modifier × file_modifier / strength

其中：
  reference_modifier = 1.0 / (1.0 + reference_count × 0.2)
  file_modifier = 0.3（关联文件仍在活跃编辑）
                  1.0（关联文件无变化 / 无关联文件）
  strength = 累积访问强度（初始 1.0，每次被引用 +0.1，对应 Knox-MS 的 β 因子）

strength 的作用：
  - strength 越大 → effective_decay 越小 → 压缩越慢
  - 实现"越用越牢固"的正反馈（时频双因子：时间衰减 + 频率强化）
  - 与 reference_modifier 的区别：ref_count 是离散引用次数用于 modifier，
    strength 是连续累积强度直接调制 decay 速率

例：
  被引用 0 次           → reference_modifier = 1.0, strength = 1.0
  被引用 5 次           → reference_modifier = 0.5, strength = 1.5（decay 再除以 1.5）
  被引用 10 次          → reference_modifier = 0.33, strength = 2.0（decay 再除以 2.0）
  关联文件仍在活跃编辑  → file_modifier = 0.3
```

### 4.4 压缩等级判定（v5 修订：添加窗口占比维度）

> 默认基准窗口 128K。阈值同时标注绝对值与窗口占比，两者等效；窗口大小变化时以占比为准。

| 压缩等级 | 触发条件（tool block） | 触发条件（推理链） | 窗口占比 (tool) | 窗口占比 (推理) | 类型约束 | 可逆性 |
|---------|----------------------|-------------------|----------------|-----------------|---------|--------|
| L0 | effective_decay < 16K | effective_decay < 32K | < 12.5% | < 25% | 无条件 | — |
| L1 | effective_decay 16K-48K | effective_decay 32K-96K | 12.5%-37.5% | 25%-75% | tool_result 可做 | 可逆 |
| L2 | effective_decay 48K-128K | effective_decay 96K-256K | 37.5%-100% | 75%-200% | tool_result 可做 | 可逆 |
| L3 | effective_decay ≥ 128K | effective_decay 256K-512K | ≥ 100% | 200%-400% | tool_result 上限 L3 | 可逆 (expand) |
| L4 | effective_decay ≥ 128K | effective_decay ≥ 512K | ≥ 100% | ≥ 400% | tool_call / 推理链 / 失败 / 废弃 | 不可逆 |

**task_group 加速系数（v6 新增）**：

已完成 task_group 中的 step，decay 加速以促进更激进的压缩：

```
若 step 所属 task_group 已完成（所有 step 均 ≥ L3 且 ref_count=0）：
  effective_decay × 1.5（加速 50%）

跨 task_group 引用保护：
  若 step N（旧 task_group）被 step M（当前 task_group）引用：
    → 不应用加速系数（该 step 跨任务重要，保持正常衰减）
    → strength 额外 +0.2
```

### 4.5 行业基准参考：压缩策略编排

以下为当前主流 Agent 产品的压缩阈值和实践，作为本设计编排经验的补充参考：

| 产品 | 压缩触发阈值 | 策略特点 |
|------|------------|---------|
| **Claude Code** | ~92% 窗口 | 极限压榨，榨干上下文每一 token 才触发 compaction；API 单参数控制 |
| **Gemini CLI** | ~70% 窗口 | 稳健保守，宁可频繁压也要保稳定性 |
| **Hermes** | 80% 窗口（默认，可配） | 双层：agent 压缩器 50% + gateway 兜底 85%；offset 设计避免过早触发 |
| **OpenCode** | 75% 窗口 | 硬编码，用户反馈大窗口模型（Gemini 1M）性能劣化始于 30%，需更低阈值 |
| **Letta (MemGPT)** | 自适应（LLM 自主决策） | 虚拟内存模型：主上下文(RAM) + 外部上下文(Disk)，LLM 通过 function call 自主换页 |
| **ACON (Microsoft)** | 4096(历史)/1024(观测) tokens | 优化压缩准则迭代精炼，distill 到小模型，保持精度同时削减 26-54% token |
| **Context Gateway** | 75% 窗口 | 后台异步压缩（便宜模型预计算摘要），触发时 swap 替代同步等待 |

**三个普适模式**：

1. **Head protect + Middle summarize + Tail preserve**：系统提示 + 首条消息保护在头部不动，中间做摘要压缩，尾部保留最近 N 轮原文——几乎所有产品的共同选择。
2. **窗口百分比触发而非绝对值**：市面上没有使用绝对 token 值作为压缩阈值的生产系统，一律使用窗口占比。
3. **压缩降级优于丢弃**：Hermes 的 bug fix 教训——压缩失败时应保留原文而非静默丢弃。对应本设计 §11.1 的 pending_buffer 降级策略。

### 4.6 压缩触发层级总览（v5 明确，v6 扩展为五层）

从轻到重的五层防线：

```
第一层 · per-step 自动压缩（§4.4）
  触发：effective_decay 越过各等级阈值
  动作：按等级升级 L0→L1→L2→L3，更新 compress.jsonl
  范围：单 step，低延迟，不阻塞

第二层 · 空闲巩固（idle consolidation，v6 新增，借鉴 Knox-MS φ7"睡眠巩固"）
  触发：主 agent 空闲超过 N 步（默认 10 步，可配置），或 pending_buffer 合并后
  动作：
    - prune: refs.jsonl 中 ref_count=0 且 effective_decay 超过 L3 阈值的 step
      → 预标记为 L4（mark pending），等下一个批次边界统一执行（不阻塞主流程）
    - strengthen: ref_count 高的 step → strength 值保持，确保衰减更慢
    - merge: 相邻同类型 L2/L3 掩码合并（v5 §1.2 二级合并规则的批量版）
    - task_group 归档检查（§2.4.3）：满足条件的 task_group 执行归档
  范围：全局扫描，批量处理，后台异步执行
  设计要点：空闲巩固只做预标记，不直接升级压缩等级，避免与正在进行的压缩冲突

第三层 · 部分拼接压缩（针对特定段）
  触发：当特定分支或文件集合的总上下文膨胀，需要更高 Lx 折叠
  动作：对目标 step 集合提升压缩等级（如 L1→L3），减少该分支总占比
  范围：活跃路径上的特定段，不影响无关分支

第四层 · 二道检测线（全局 summary）
  触发：用户任务阶段已过、主任务中心已转移、上下文需要整理
  动作：LLM 全局 summary → 压缩后备份 refs.jsonl（checkpoint）
  对应 §6 全局碎片整理的四种触发条件

第五层 · 最后警戒线（应急，§3.2）
  触发：总 token 即将超过上下文窗口上限
  动作：全局 LLM summary → fallback 分片压缩 → 展开补回
```

**空闲巩固与反思式整体节选的关系**：空闲巩固是后台自动的 prune + strengthen + merge，不依赖 LLM 判断。反思式整体节选（第四层全局 summary）则是 LLM 驱动的语义级整理，只在特定触发条件下执行。两者互补——空闲巩固清理零引用垃圾，减轻全局 summary 的压力。

## 五、批次压缩架构与缓存稳定（与 v4 相同，确认）

### 5.1 上下文布局

物理存储上 L0 jsonl 为线性 append-only 序列；运行时按 step_id 升序从 refs.jsonl 获取活跃 step 列表，从 L0 jsonl 加载原文拼接材料化视图。

```
┌──────────┬──────────┬──────────────────────────────────────────────┐
│  head     │  skill   │     raw_history (追加不修改)                    │
│  ~5.5K    │  ~10K    │  step_1 ... step_2 ... step_N                  │
│  不可变    │  不可变   │  仅追加，不修改已有内容                          │
├──────────┴──────────┴──────────────────────────────────────────────┤
│ ◄── 缓存命中区 (~15.5K) ──►│◄── 缓存失效区（但会增长）──►│◄─ tail ─►│
│                              │                            │ HintBlock│
│                              │                            │ 注入区   │
└──────────────────────────────────────────────────────────────────────┘

逻辑视图：按 step_id 升序从 refs.jsonl 获取活跃 step →
  head + skill + [step 序列按 step_id 升序拼接]

HintBlock 注入位置（v6 明确）：
  运行时动态信息（上下文压力警告、当前任务阶段提示等）以 HintBlock 形式
  追加在 tail 区，绝不侵入 head_buffer，保持 prefix cache 字节稳定性。
  借鉴 AgentScope HintBlock 模式 + Knox-MS 动态上下文组装的 C_goal 尾部放置。
```

### 5.2 批次压缩流程（v5 明确）

> 执行者归属：Step 1-3 框架纯算术、Step 4 调 3B（兜底主模型）、Step 5-6 框架 IO + 规则、Step 7 主模型按需、Step 8 框架诊断。8 步中 6 步无 LLM。

```
Step 1 · 扫描（框架）
  输入：refs.jsonl 当前活跃路径上的 step_id 列表
  动作：
    - 对每个 step，查 last_referenced_at_step，从 L0 jsonl 逐行累加 token_count
      得到 raw_decay（O(步数差)，不走全文 tokenize）
    - 查 refs.jsonl 获取 ref_count → 算 reference_modifier
    - 查 refs.jsonl 获取 strength → 调制衰减速率
    - 查 related_files 是否仍在活跃编辑 → 算 file_modifier
    - 查 task_group_id 是否已完成 → 算 task_group 加速系数（§4.4）
    - 得 effective_decay = raw_decay × ref_mod × file_mod / strength × task_group_mod
  输出：候选列表 [{step_id, current_level, effective_decay, step_type, segments, task_group_id}]

Step 2 · 分级（框架 + Redis 语义安全网）
  输入：候选列表
  动作：
    - 查 §4.4 阈值表：按 step_type（tool 走左列，reasoning/plan/failed 走右列）
      定位 effective_decay 所在区间 → 目标 level
    - 若 step_type=tool 且 segments 存在：
        call 段 max_compression_level=4，取 min(目标 level, 4)
        result 段 max_compression_level=3，取 min(目标 level, 3)
        若目标 level ≤ 当前 level → 该段跳过（不重复压缩）
    - 语义安全网（v6 新增，借鉴 Knox-MS 多信号检索）：
        当 effective_decay 在阈值边界的 80%-120% 区间（模糊地带）时：
        → 查 Redis：context_search_redis(session_id, step.text, limit=3)
        → 若 top-1 score > 0.6 → 暂缓压缩，标记 semantic_hold=true
        → 若 score < 0.35（低于召回阈值）→ 正常压缩
        → 中间地带 → 按原规则压缩
        （Redis 不可用时跳过此检查，按原规则处理）
    - 过滤：目标 level == 当前 level 的条目直接移除
  输出：待压缩列表 [{step_id, target_level, segments_to_compress, semantic_hold}]

Step 3 · 预估（框架）
  输入：待压缩列表
  动作：
    - 按经验比率估算节省量：
        L0→L1: ~30% 节省（去噪）
        L1→L2: ~50% 节省（去推理）
        L2→L3: ~70% 节省（仅掩码）
        →L4: 100% 节省（丢弃）
    - 总节省 = Σ (token_count × 比率)
    - 若总节省 < min_saving_threshold（默认 2K tokens）→ 跳过本轮，等下一批次
  输出：确认执行列表 或 跳过信号

Step 4 · 执行（3B 模型，不可用时主模型兜底）
  输入：确认执行列表 + 各 step 原文（从 L0 jsonl 按需加载）
  动作：
    - 组装 prompt：system = 压缩指令（等级定义 §2.3），user = 原文
    - 批量调用 3B 模型（本地 Qwen2.5-3B，80-100 tok/s）
    - L1 去噪：去掉重复日志行、空白、冗余格式
    - L2 事实保留：提取路径/配置值/错误消息，丢弃过渡性推理
    - L3 掩码：框架提取结构体（step_id/工具名/参数）+ LLM 拼接意图总结
    - 超时/不可用 → 主模型兜底
  输出：{step_id: compressed_text, level, content_hash}

Step 5 · 落盘（框架）
  动作：
    - 对每个压缩产物，写临时文件 {uuid}.compress.tmp
    - 逐行更新或新增对应的 step_id 行：
        level → 新等级
        content_hash → sha256(compressed_text)
        compressed_at_step → 当前 step
        compressed_at_header_version → 当前 header 版本
    - 原子 rename .tmp → .jsonl（避免写入中断损坏）
    - 若 rename 失败 → 回滚，保留上版本
  输出：更新后的 compress.jsonl

Step 6 · 机械验证（框架，第一层格式检查器）
  动作：
    - compress.jsonl 每行必含 step_id / level / content_hash
    - level 值在 0-3 范围
    - content_hash 格式 = "sha256:{64位hex}"
    - 压缩后产物长度 ≤ 原长度（压缩不能膨胀）
    - 无重复 step_id 行
  输出：通过 / 失败（失败则回滚 Step 5）

Step 7 · 语义审计（主模型，按需）
  触发：手动触发 或 本次为全局压缩（§4.6 第三层）
  动作：context_inspector skill — 主模型抽查压缩后内容是否保留关键信息
  输出：通过 / 需修正的 step_id 列表

Step 8 · 诊断（框架）
  动作：更新 CacheShape 指标
    - head 区 token 数
    - 活跃路径总 token 数
    - 各等级 step 数量分布（L0/L1/L2/L3/L4 计数）
    - 本次压缩节省量
  输出：写入诊断日志
```

### 11.1 pending_buffer 与小模型 API 降级（v5 新增）

### 12.2 context_search：BM25 被动查证工具（v5 新增，替代 v4 heat_score）

**定位**：BM25 是 `context_search` 工具的检索后端，LLM 需要查证历史、确认幻觉、追溯过往决策时主动调用。不参与压缩判定的自动计算。

**借鉴**：ReasonX 的 `history` 工具（`internal/history/search.go`）— LLM 调用 `history(search, query=...)` → BM25 排名返回命中 → LLM 跟进 `history(around, ...)` 读上下文窗口。

**context_search 工具接口**：

```
context_search(query, 
               scope=["current_session" | "archive" | "all"],
               kind=["tool_call" | "tool_result" | "reasoning" | "user_message"],
               limit=8)
  → [{step_id, score, snippet, step, kind, session_id}]

context_surround(step_id, before=3, after=3)
  → 返回该 step 附近的上下文窗口
```

**scope 参数说明**：默认仅 `current_session`。`archive` 和 `all` 为可选扩展——跨 session 检索涉及全量 L0 jsonl 扫描，IO 代价高，需显式开启。当前阶段不建议默认全局搜索。
**索引策略**（借鉴 ReasonX）：每次调用现建索引，不维护持久索引 — 扫描 L0 jsonl → tokenize → BM25Score → 排序 → MakeSnippet。`KeepTopRelativeScore(0.15)` 动态切噪声。

**Tokenizer**（借鉴 ReasonX）：拉丁词 → lowercase + 连续字母/数字/下划线；CJK → 逐字拆分。搜 CJK 时可搜索原始查询字符串作为整词匹配的补充。

**实现参考**：ReasonX `retrieval/bm25.go` (178 行纯 Go，零外部依赖) — 七个函数即可完整实现，可直接移植到目标语言。

### 12.3 Pi 的 retainedTail 双模式（与 v4 相同）

### 12.4 fact_block：压缩流程中的事实结晶（v6 新增，草案）

**定位**：fact_block 是压缩流程的副产品——当 step 被压缩到 L2（事实保留）阶段时，如果满足升级条件（高频引用 / 跨任务引用 / 用户标记 / 配置值 / 错误模式），其中的关键事实会被结晶为 `fact_block`，注入到 Slot 2（process_area）前端，使其在当前任务期间持续可见。

**与传统记忆模块的区别**：

| 传统记忆模块（MemGPT/Letta/Mem0） | fact_block 机制 |
|--------------------------------|----------------|
| 独立的"记忆提取→存储→检索"管线 | 压缩流程的副产品，无独立管线 |
| 写入外部向量数据库 | 沉淀在 `{uuid}.facts.jsonl`（三件套的补充文件） |
| 检索时走 RAG 召回 | 升级后直接在上下文内可见（ICL 生效） |
| 需要维护额外的存储和索引 | 复用现有三件套 + Redis，零额外基础设施 |

**核心流程**：

```
step 进入尾部区（Slot 3）→ 被推向过程区（Slot 2）→ 压缩到 L2
    │
    │ 满足升级条件？
    │
    ├── 否 → 继续正常压缩（L3 → L4）
    │
    └── 是 → 3B 模型提取结构化事实 → 结晶为 fact_block
              → 注入 Slot 2 前端 → 参与引用追踪 → 生命周期独立管理
```

**升级条件**（详见 §15.4.1）：ref_count ≥ 3 且 strength ≥ 1.3 / 跨 task_group 引用 / 用户显式标记 / 配置值正则匹配 / 错误→解决方案配对。

**fact_block 格式**：

```
[fact_block | sources: step_42, step_55 | confidence: high]
  关键事实 1: Redis 连接池配置已迁移至 redis_config.py
  关键事实 2: 生产环境 REDIS_TIMEOUT=30s
[/fact_block]
```

**存储**：`{uuid}.facts.jsonl`，优先级 4（在三件套 + Redis 之后）。fact_block 有独立生命周期：产生 → 活跃（参与 ICL）→ 降级（ref_count=0）或沉淀（跨 ≥ 3 个 task_group → 候选进入 head_buffer）。

**与 Route 4 的关联**：fact_block 机制是"ICL as Meta-Learning"的工程落地——上下文不只是"给模型看的信息"，而是"模型从中学习的产物"。详见 §15.6。

## 附录 A：多产品源码验证与 AgentScope 架构参考（2026-07-27）

> 基于 Kimi Code (`packages/agent-core`)、Pi (`packages/agent` + `packages/coding-agent`)、ReasonX (`internal/agent/`) 三家源码验证报告，以及 AgentScope (`src/agentscope/`) 架构分析，提炼对本设计的参考价值。

### A.1 三家核心策略对比

| 维度 | Kimi Code | Pi | ReasonX |
|------|-----------|-----|---------|
| **压缩触发** | 85% + 50K reserved | `contextWindow - 16384` | 四级比率 (50%/60%/80%/90%) |
| **保留策略** | Head 2K + Tail 18K | keepRecentTokens=20K | defaultTailTokens=16K + pinned first user |
| **摘要方式** | LLM 全文摘要 + 迭代更新 | LLM 摘要 + 迭代更新 + branch summary | summarize fold + 机械折叠兜底 |
| **存储格式** | wire.jsonl + state.json | JSONL 树形 (parentId 链接) | JSONL + events.jsonl + checkpoint |
| **缓存保护** | 无显式机制 | 无显式机制 | cache-stable prefix + cache_shape 诊断 |
| **工具结果处理** | 无特殊处理 | 无特殊处理 | 多级 snip (read-only 80+12行, side-effecting 40+40行) + 32KB 上限 |
| **历史检索** | 无 | 无 | BM25 被动工具 (history/around) |
| **扩展机制** | 无 | Extension Hooks (session_before_compact/tree) | 无 |

### A.2 v5 已吸收的三家优势

- **ReasonX** → 多级压缩思想（L1-L4 对应 soft/snip/compact/force）、BM25 被动工具、cache-stable prefix、机械折叠兜底、首条消息 pinning
- **Pi** → 迭代摘要更新、retainedTail 双模式、branch summary（树形结构的 refs.jsonl 替代）、extension hooks（中间件链）
- **Kimi Code** → Head+Tail 分割（v5 的 head_buffer 不可压缩区）、elision marker 思想

### A.3 AgentScope 架构概述

AgentScope (`src/agentscope/`) 采用**洋葱中间件模型**而非内置压缩逻辑，核心由以下层次组成：

1. **AgentState** — 持久化状态层（`summary` + `context` + `middle_context`）
2. **ContextConfig** — 配置层（`trigger_ratio=0.8`、`reserve_ratio=0.1`、`tool_result_limit=50000`、`compression_prompt`、`summary_schema`）
3. **Agent.compress_context** — 核心压缩逻辑（token 计数 → 阈值判断 → 分割 → 结构化摘要 → 原子更新）
4. **MiddlewareBase** — 7 个钩子点的中间件拦截体系（含 `on_compress_context`）
5. **具体中间件** — Budget、RAG、长期记忆（AgenticMemory/Mem0/ReMe）等

### A.4 AgentScope 值得吸收到 v5 的处理方式（按优先级）

#### 优先级 1：结构化摘要 Schema

AgentScope 的压缩通过 `generate_structured_output()` 生成严格 JSON Schema 格式的五维摘要：

```
task_overview         → 用户核心请求和成功标准
current_state         → 已完成的工作
important_discoveries → 技术约束、决策理由、错误及解决方案
next_steps            → 待完成具体操作
context_to_preserve   → 需跨压缩保留的用户偏好、领域细节
```

**对比 v5**：v5 的 L2（事实保留）和 L3（掩码）没有规定摘要的结构化格式。AgentScope 的做法确保摘要不遗漏关键维度，尤其 `context_to_preserve` 字段显式让 LLM 自己决定什么值得保留。

**建议**：v5 的全局 summary（§4.6 第三层/第四层压缩）可采用类似的结构化 schema，而非自由文本。

#### 优先级 2：Tool Call/Result 配对保护

AgentScope 在 `_split_context_for_compression()` 中分割上下文时，确保 `ToolCallBlock` 和对应的 `ToolResultBlock` 不被拆到压缩/保留两侧。如果出现孤立的 `ToolResultBlock`（没有对应的 call），自动将边界前移到配对的 `ToolCallBlock`。

**对比 v5**：v5 §1.2 区分了 tool_call（可 L4 丢弃）和 tool_result（L3 封顶），但没显式讨论分割时的配对完整性。

**建议**：在 §5.2 批次压缩 Step 2（分级）中增加配对约束——压缩 tool_result 时，若对应的 tool_call 也在压缩范围，两者一起处理；若 tool_call 在保留区而 tool_result 在压缩区，保持当前设计（result 可独立压缩为掩码）。

#### 优先级 3：Context Buffer 预警机制

AgentScope 在 token 数超过 `(trigger_ratio - context_buffer_ratio) * context_size` 时（即压缩阈值之前 20%），向 agent 注入上下文长度警告（`<context-length>` HintBlock），让 agent 自行意识到即将压缩。

**对比 v5**：v5 的 ReasonX 式多级阈值（soft notice → snip → compact → force）已有类似思想，但 AgentScope 的做法更直接——让 LLM 自己感知压力并可能主动精简输出。

**建议**：v5 第一层 per-step 自动压缩中，可在 soft notice 阶段向 agent 注入 token 预算警告。

#### 优先级 4：HintBlock 注入模式

AgentScope 不修改 system prompt 来注入运行时信息（时间、任务状态、上下文长度警告），而是使用 `HintBlock` 追加到对话上下文中。这保持了 system prompt 的字节稳定性，有利于 prefix cache 命中。

**对比 v5**：v5 §1.1 的 head_buffer 不可变区 + §5.1 的缓存命中区设计与此理念一致。AgentScope 的 HintBlock 是一个具体的实现模式。

**对比 ReasonX**：ReasonX 的 cache-stable prefix 也是同样的理念——系统前缀不变，变化放在尾部。

### A.5 AgentScope 的不足（相比三家）

| 不足 | 说明 |
|------|------|
| **无多级压缩** | 只有"压缩/不压缩"二元判断，没有 L1-L4 渐进式降级 |
| **无引用追踪** | 没有 ref_count / decay 机制，所有消息等权对待 |
| **无树形结构** | 线性上下文，不支持分支/嫁接/子 agent fork |
| **无 cache 诊断** | 没有 CacheShape 类似的缓存前缀变化追踪 |
| **无 BM25 检索** | 长期记忆依赖外部服务（mem0/ReMe），没有内置的历史检索 |
| **Token 估算粗糙** | `len(text.encode("utf-8")) / 4`，对 CJK 文本误差大 |
| **压缩触发粗糙** | 仅 80% 单一阈值，没有 ReasonX 式的多级渐进 |

### A.6 综合结论

AgentScope 的核心价值在于**中间件架构的可扩展性**（7 钩子点 + 洋葱模式 + Offloader Protocol），但在上下文管理的深度上不如 Kimi Code / Pi / ReasonX。v5 设计已经从三家源码中吸收了更深层的机制（引用距离驱动、多级压缩、BM25 被动检索、树形拓扑），AgentScope 的贡献更多在**接口设计层面**——结构化摘要 Schema、Tool Call/Result 配对保护、HintBlock 注入模式、Context Buffer 预警。

## 十五、记忆的持久化事实提炼沉淀（草案）

> **状态**：草案 v1，待评审
> **关联**：Route 4（In-Context Learning as Meta-Learning）工程落地探索
> **前置分析**：MemGPT 和你的设计都在优化"ICL 的容器"（让上下文更大、更智能），但还没有触及"ICL 作为学习机制"（让模型从上下文中提取可迁移的策略）。本节是跨出这一步的草案。

### 15.1 设计哲学：不做显式记忆提取

**核心原则**：Agent 不需要内置独立的"记忆提取→存储→检索"管线。

理由：

| 传统记忆管线（MemGPT/Letta/Mem0 模式） | 本设计的自然沉淀路径 |
|--------------------------------------|-------------------|
| 显式调用"记忆模块"提取事实 | 压缩流程自身就是事实提炼过程 |
| 写入外部向量数据库 | 事实沉淀在压缩产物和 fact_block 中 |
| 检索时走 RAG 召回 | 升级后的事实在上下文内直接可见（ICL 生效） |
| 需要维护额外的存储和索引 | 复用现有三件套 + Redis，零额外基础设施 |

**关键洞察**：压缩从 L0→L1→L2→L3 的过程，本身就在做"去噪→保留事实→提炼掩码"。这个流程天然就是记忆沉淀——不需要额外的"记忆提取"步骤，只需要在压缩流程的关键节点上**拦截和结晶**。

```
传统路线：  对话 → [记忆提取模块] → 向量数据库 → [RAG 召回] → 上下文
本设计路线：对话 → [压缩流程] → L2 事实保留 → [结晶拦截] → fact_block 升级
              ↑ 不需要额外模块          ↑ 复用现有流程     ↑ ICL 内生效
```

**v6 设计哲学升级——从全局总结到重点 step 提取摘要**：

传统压缩思路是"给出整个对话的总结"（全局 summary），这有两个问题：
1. **LLM 输出压力大**——长文本生成消耗 token 和延迟
2. **缓存不友好**——全局 summary 每次变化导致 prefix cache 大面积失效

v6 迁移为：**LLM 驱动的压缩从"给出整个对话的总结"迁移为"重点 step 的提取摘要，供后续组装"**。好处：
- **利用缓存**——已有 step 的摘要不变，prefix cache 命中区不被动摇
- **缓解输出压力**——每次只提取单个 step 的摘要（短文本），而非生成整段总结
- **可组装**——结构化摘要可按 keywords/depends_on 动态拼接，按需组装上下文

### 15.2 上下文三槽位模型

在现有布局（§5.1）基础上，明确三个功能槽位的职责：

```
┌─────────────────────────────────────────────────────────────────────┐
│ Slot 0 · head_buffer（~5.5K）                                       │
│ 宪法准则 / 操作禁止 / 初始目标 / 首条消息 / skill_zone                │
│ 特性：永不压缩，prefix cache 命中区                                   │
│ 记忆角色：沉淀终点——只有经过验证的核心事实才能到达这里                   │
├─────────────────────────────────────────────────────────────────────┤
│ Slot 2 · process_area（中间区，不断追加）                             │
│ step_1 ... step_2 ... step_N（活跃 step 序列）                       │
│ 特性：引用距离驱动压缩，L0→L1→L2→L3→L4 渐进降级                      │
│ 记忆角色：自然沉淀区——step 在此被压缩、提炼、结晶为 fact_block          │
├─────────────────────────────────────────────────────────────────────┤
│ Slot 3 · tail_area                                                  │
│ 最近 N 轮原文 + HintBlock 注入区                                     │
│ 特性：保持原文，不主动压缩                                            │
│ 记忆角色：默认落点——新 step 默认留在此处，等待被压缩刷新                │
└─────────────────────────────────────────────────────────────────────┘
```

### 15.3 默认行为：留在尾部区

**所有新产生的 step 默认留在尾部区（Slot 3），不做任何显式记忆提取或存储。**

理由：

1. **尾部区是天然的"工作记忆"**——最近的信息保持原文，模型可以直接 ICL
2. **压缩流程会自动处理**——随着新 step 追加，旧 step 被推向 Slot 2，effective_decay 越过阈值时自动触发压缩
3. **strength 字段自然积累**——被多次引用的 step 衰减更慢，自然"浮"在活跃区域
4. **不需要额外的记忆管理开销**——没有 embedding 计算、没有向量写入、没有独立检索调用

```
新 step 产生
    │
    ▼
默认进入 tail_area（Slot 3）
    │
    │ 随着新 step 追加，旧 step 被推向 process_area（Slot 2）
    │
    ▼
在 process_area 中自然经历压缩流程：
  L0（原文）→ L1（去噪）→ L2（事实保留）→ L3（掩码）→ L4（丢弃）
    │
    │ 在 L2/L3 阶段，如果满足升级条件 → 结晶为 fact_block
    │
    ▼
fact_block 注入 process_area 前端（或满足条件时进入 head_buffer）
```

**这意味着**：Agent 不需要"主动记住"任何东西。所有记忆行为都是压缩流程的副产品——就像人不需要"主动记住"反复用到的知识，自然就会记住一样。

**v6 澄清：尾部区清理 ≠ L2 压缩，是两套不同机制**：

| 机制 | 作用对象 | 触发条件 | 目的 |
|------|---------|---------|------|
| **尾部区清理** | 从长期记忆库/Project Fact Store 提取并注入尾部区的 fact_block | 50 步后 ref_count=0 且 task_group 完成 | 清除不再相关的"外来"事实，释放尾部空间 |
| **L2 压缩** | process_area 中被推向 Slot 2 的原始 step | effective_decay 越过 L2 阈值 | 从原始操作记录中提炼事实，结晶为 fact_block |

两者独立运作：尾部区清理是"新陈代谢"（排出无用信息），L2 压缩是"消化吸收"（从信息中提取价值）。

### 15.4 升级条件：从尾部区进入过程区（Slot 2）

特定情况下，step 中的关键事实可以被**升级**，以 `fact_block` 形式注入到 Slot 2 的前端区域，使其在当前任务期间持续可见。

#### 15.4.1 升级触发条件

升级由**框架侧自动判定**，不需要 LLM 显式调用"记忆存储"。触发条件基于现有的 refs.jsonl 信号：

| 条件 | 阈值（草案） | 信号来源 | 理由 |
|------|------------|---------|------|
| **高频引用** | ref_count ≥ 3 且 strength ≥ 1.3 | refs.jsonl | 被反复引用的 step 包含当前任务的关键事实 |
| **跨任务引用** | step 被 ≥ 2 个不同 task_group 引用 | refs.jsonl 的 task_group_id | 跨任务有价值的事实值得持续可见 |
| **用户显式标记** | 用户消息中出现 pin/记住/重要等意图 | LLM 意图识别 | 用户明确要求保留的信息 |
| **配置/环境值** | step_type=tool 且 result 包含配置值/路径/环境变量 | 框架正则匹配 | 配置值是事实性最强的信息，压缩损失不可接受 |
| **错误模式** | step_type=failed 且后续 step 引用了该失败的解决方案 | refs.jsonl | "踩过什么坑、怎么解决的"是高价值事实 |

**v6 新增——重点 step 摘要的自动触发条件**（与 fact_block 升级并行，但独立判定）：

除上述 fact_block 升级条件外，以下场景自动触发**单 step 摘要提取**（写入 step_summaries.jsonl，供后续组装）：

| 触发条件 | 信号来源 | 说明 |
|---------|---------|------|
| **高置信度 fact_block 生成** | 3B 模型输出 confidence=high | 提取出关键事实（配置值、错误根因）时，立即生成该 step 的结构化摘要 |
| **用户显式标记** | 用户输入含 [重要]/pin/记住 等意图 | 用户明确要求保留的信息，立即生成摘要 |
| **错误/分支点** | LLM 输出 error 或 replan 步骤 | 任务路径切换时，记录"为什么切换"的决策摘要 |

**降级方案**：若 3B 模型质量不稳定，用规则兜底：
- 正则匹配（如 `^配置已更新：(.*)$` → 提取参数名/值）
- 标记工具调用结果（git commit、curl 等命令的返回值）

#### 15.4.2 升级流程

```
Step 1 · 扫描（框架，复用 §5.2 Step 1）
  在每步压缩扫描时，同时检查升级条件：
    - 遍历 refs.jsonl 中 effective_decay 进入 L2 区间的 step
    - 对每个候选 step，检查 §15.4.1 的五个条件
    - 满足任一条件 → 标记为 upgrade_candidate

Step 2 · 提取（3B 模型，复用 §5.2 Step 4 的调用通道）
  对 upgrade_candidate 的原文，调用 3B 模型提取结构化事实：
    输入：step 原文 + 压缩指令（"从以下操作记录中提取可复用的事实"）
    输出：fact_block 结构体（§15.4.3 格式）
    注意：与压缩共用 3B 调用批次，不额外增加调用次数

Step 3 · 注入（框架）
  将 fact_block 注入 Slot 2 前端（head_buffer 之后、活跃 step 之前）
  注入位置：紧跟 skill_zone 之后，享受 prefix cache
  注入格式：见 §15.4.3

Step 4 · 追踪（框架）
  fact_block 本身也参与引用追踪：
    - 分配虚拟 step_id（负数，与正常 step 区分，如 fb_-1, fb_-2）
    - 记录在 refs.jsonl 中，ref_count 反映 fact_block 被引用的频率
    - fact_block 的 decay 独立计算（不受原 step 的 decay 影响）
```

#### 15.4.3 fact_block 格式

```
[fact_block | sources: step_42, step_55 | confidence: high]
  关键事实 1: Redis 连接池配置已迁移至 redis_config.py
  关键事实 2: 生产环境 REDIS_TIMEOUT=30s（原 config.py 中的值）
  关键事实 3: 旧 config.py 中的 REDIS_HOST 已被废弃，不再使用
[/fact_block]
```

字段说明：

| 字段 | 来源 | 说明 |
|------|------|------|
| sources | 框架提取 | 事实来源的 step_id 列表，可追溯 |
| confidence | 3B 模型输出 | high/medium/low，基于原文的明确程度 |
| 关键事实 | 3B 模型提炼 | 从原文中提取的结构化事实，每条一行 |

#### 15.4.3.1 结构化 step 摘要格式（v6 新增）

与 fact_block 并行，对重点 step 生成**结构化摘要**，存入 `step_summaries.jsonl`。摘要不是自由文本，而是可组装的元数据：

```json
{
  "ref": "step_42",
  "summary": "用户确认 Redis 超时阈值从 500ms 调整为 2000ms",
  "depends_on": ["fb_-1"],
  "keywords": ["redis", "timeout", "config"],
  "session_id": "sess-abc123",
  "fact_version": "fb_-1_v1",
  "created_at_step": 60
}
```

字段说明：

| 字段 | 来源 | 说明 |
|------|------|------|
| ref | 框架 | 源 step_id，用于追溯原文 |
| summary | 3B 模型 | 一句话摘要，描述该 step 的关键决策/事实 |
| depends_on | 框架 | 依赖的 fact_block ID 列表，确保组装时逻辑连贯 |
| keywords | 3B 模型 + 框架 | 技术术语列表，用于后续检索和组装 |
| session_id | 框架 | 归档时自动注入，标识来源 session |
| fact_version | 框架 | 关联 fact_block 的版本号（如 fb_-1_v1），用于过期检测 |
| created_at_step | 框架 | 摘要生成时的 step 编号 |

**组装优势**：可按 keywords 或 depends_on 拼接逻辑链。例如：config 相关摘要 → 自动聚合所有配置变更史。

**组装伪代码**：

```python
def build_context(task_query: str):
    relevant_facts = search_facts(keywords=extract_keywords(task_query))  # 1. 先找相关 fact
    step_ids = [fact["sources"][0] for fact in relevant_facts]            # 2. 追溯来源 step
    summaries = load_summaries(step_ids)                                  # 3. 仅加载关键摘要
    return "\n".join([f"[{s['ref']}] {s['summary']}" for s in summaries]) # 4. 动态拼接
```

#### 15.4.4 fact_block 的生命周期

```
产生：从 L2/L3 压缩中结晶，注入 Slot 2 前端
    │
    ▼
活跃：在当前 task_group 内持续可见，参与 ICL
    │
    ├── 被模型引用 → strength 增加，保持活跃
    │
    ├── task_group 完成 → fact_block 进入降级流程：
    │     │
    │     ├── ref_count > 0（仍被新任务引用）→ 保持活跃，不降级
    │     │
    │     └── ref_count = 0（无引用）→ 降级为 L3 掩码
    │           │
    │           └── 后续若再次被引用 → 重新升级
    │
    └── 累积 ≥ 5 个 fact_block 且跨 ≥ 3 个 task_group → 候选沉淀到 Slot 0
          │
          ▼
        沉淀：合并进 head_buffer 的"已验证事实"子区（需全局 summary 确认）
```

#### 15.4.5 什么值得升级，什么不值得

| 类型 | 是否升级 | 理由 |
|------|---------|------|
| 反复引用的 tool_result（配置值/路径/错误消息） | **升级** | 事实性强，压缩损失不可逆 |
| 跨 task_group 被引用的决策理由 | **升级** | 避免重复推理 |
| 用户显式标记的偏好 | **升级** | 用户意图明确 |
| 错误→解决方案的配对 | **升级** | 高价值经验事实 |
| 一次性查询结果 | **不升级** | 留在尾部自然淘汰 |
| 推理链 / 规划 | **不升级** | 模型可重新生成 |
| 中间计算过程 | **不升级** | 已被后续结论覆盖 |

#### 15.4.5.1 L2 掩码的事实质疑否定机制（v6 新增）

L2 级别的掩码除了 confidence 三级（high/medium/low）外，还允许因**事实质疑**而被否定：

**触发条件**：

| 质疑来源 | 信号 | 处理方式 |
|---------|------|---------|
| **后续 step 矛盾** | 新 step 的 tool_result 与已有 fact_block 的事实值冲突（如配置值不同） | 旧 fact_block 标记 `negated_by: step_N`，降级为 L3 掩码 |
| **用户显式否定** | 用户消息中出现"不对""错了""不是这样"等否定意图，且引用了某个 fact_block | 被引用的 fact_block 标记 `negated_by: user_at_step_N`，降级 |
| **主模型审计否定** | 全局 summary 时主模型判断某 fact_block 与当前上下文矛盾 | 标记 `negated_by: audit_at_step_N`，降级 |

**否定后的处理**：

```
fact_block 被否定
    │
    ├── 有替代事实（新 step 提供了正确值）
    │   → 旧 fact_block 降级 + 新 fact_block 自动升级
    │   → step_summaries.jsonl 中对应摘要标记 fact_version 为 deprecated
    │
    └── 无替代事实（用户说"错了"但没给正确值）
        → 旧 fact_block 降级为 L3 掩码
        → 对应摘要标记 status: "negated"，保留但不再参与组装
```

**与 §15.5.3 冲突检测的关系**：§15.5.3 处理的是两个 fact_block 之间的自动覆盖（后产生的覆盖先产生的），本节处理的是**主动质疑否定**——不仅覆盖，还显式标记"旧事实已被否定"，确保摘要链的可追溯性。

### 15.5 实现草案：与现有压缩流程的衔接

#### 15.5.1 修改 §5.2 批次压缩流程

在现有 8 步流程中，插入升级判定和 fact_block 注入：

```
Step 1 · 扫描（框架）
  现有逻辑 + 新增：
    - 同时检查 §15.4.1 升级条件
    - 输出增加 upgrade_candidates 列表

Step 2 · 分级（框架 + Redis 语义安全网）
  现有逻辑 + 新增：
    - upgrade_candidates 中的 step 暂缓 L3/L4 压缩
    - 保留 L2 级别原文供 fact_block 提取

Step 3 · 预估（框架）
  现有逻辑 + 新增：
    - 估算 fact_block 注入后的 token 开销
    - fact_block 预算上限：总窗口的 5%（约 6.4K tokens @128K 窗口）
    - 超出预算 → 只升级 confidence=high 的候选

Step 4 · 执行（3B 模型）
  现有逻辑 + 新增：
    - 对 upgrade_candidates 同时执行压缩 + 事实提取
    - 提取 prompt：
      """
      从以下操作记录中提取可复用的关键事实。
      只提取：配置值、文件路径、环境参数、决策理由、错误解决方案。
      不提取：推理过程、中间计算、临时状态。
      输出格式：每行一个事实，前缀 "FACT: "。
      ---
      {step_content}
      """

Step 5 · 落盘（框架）
  现有逻辑 + 新增：
    - fact_block 写入 {uuid}.facts.jsonl（三件套的补充文件）
    - 格式：{"fact_block_id":"fb_-1","sources":[42,55],"confidence":"high","facts":["...","..."],"created_at_step":60,"task_group_id":1}

Step 6 · 机械验证（框架）
  现有逻辑 + 新增：
    - 验证 fact_block 格式完整性
    - 验证 sources 中的 step_id 存在于 L0 jsonl

Step 7 · 语义审计（主模型，按需）
  现有逻辑 + 新增：
    - 全局压缩时，审计所有活跃 fact_block 是否仍然准确
    - 不准确的 fact_block → 降级为 L3 掩码

Step 8 · 诊断（框架）
  现有逻辑 + 新增：
    - 诊断指标增加：活跃 fact_block 数量、总 token 占比、平均 ref_count
```

#### 15.5.2 存储扩展：三件套 → 三件套 + 事实文件

```
优先级 1: {uuid}.jsonl                 # L0 主文件（不变）
优先级 2: {uuid}.refs.jsonl            # 引用追踪（不变）
优先级 3: {uuid}.compress.jsonl        # 压缩等级元数据（不变）
优先级 4: {uuid}.facts.jsonl           # fact_block 存储（v5 新增）
优先级 5: {uuid}.step_summaries.jsonl  # 结构化 step 摘要（v6 新增）
优先级 6: Redis ctx:{session_id}:*     # 热数据缓存层（不变）
```

**v6 新增——跨 Session 职责分离**：

| 职责 | 归属 | 说明 |
|------|------|------|
| **Session 上下文管理** | 本设计（§15） | 负责当前会话的"工作记忆"：fact_block 的生成、活跃、自动清理、摘要组装。目标是保证当前任务的效率 |
| **长期事实记忆（Project Fact Store）** | 独立工具/外部系统 | 当 Agent 在新 session 中需要历史经验时，主动调用检索工具。Session 管理器只负责**生产** fact_block 和 step_summaries，不负责跨 session 的归档和检索 |

**边界**：Session 上下文管理只负责生产和消费 fact_block / step_summaries。将这些产物汇入可供跨 session 检索的"Project Fact Store"，是另一个层面的功能（类似 `context_search` 工具的跨 session 扩展），不属于本节范畴。

`{uuid}.facts.jsonl` 格式：

```jsonl
{"fact_block_id":"fb_-1","sources":[42,55],"confidence":"high","facts":["Redis 连接池配置已迁移至 redis_config.py","生产环境 REDIS_TIMEOUT=30s"],"created_at_step":60,"task_group_id":1,"ref_count":2,"last_ref_at_step":89}
{"fact_block_id":"fb_-2","sources":[78],"confidence":"medium","facts":["用户偏好：代码风格遵循 PEP 8，缩进用 4 空格"],"created_at_step":80,"task_group_id":2,"ref_count":0,"last_ref_at_step":null}
```

fact_block 的生命周期管理：
- **产生**：Step 5 写入 facts.jsonl
- **活跃**：运行时注入 Slot 2 前端
- **降级**：ref_count=0 且 task_group 完成 → 从 facts.jsonl 移除，对应 step 正常压缩
- **沉淀**：跨 ≥ 3 个 task_group 且 ref_count 持续增长 → 候选进入 head_buffer

#### 15.5.3 冲突检测

当新提取的 fact_block 与已有 fact_block 存在语义冲突时：

```
检测方式（轻量级，框架侧）：
  1. 新 fact_block 的 sources 中的 step_id > 已有 fact_block 的 sources
     → 新事实来自更新的操作 → 新事实覆盖旧事实
  2. 新 fact_block 的 facts 中出现"已修改""已更改""已废弃"等关键词
     且涉及的文件路径/配置项与已有 fact_block 重叠
     → 判定为冲突 → 旧 fact_block 降级为 L3 掩码

不追求完美冲突检测——如果两个 fact_block 描述了同一配置的不同值，
后产生的覆盖先产生的，这是足够可靠的启发式。
```

#### 15.5.4 摘要组装流程（v6 新增）

当需要压缩上下文或为新 session 构建历史上下文时，不再做"全局总结"，而是**按需组装**：

```
组装触发条件：
  1. 全局压缩时（§4.6 第四层）——需要重建精简上下文
  2. 新 session 启动时——需要注入项目级历史事实
  3. context_inspector 触发时——需要审计上下文完整性

组装流程：
  Step 1 · 扫描活跃 fact_block（框架）
    → 从 facts.jsonl 加载当前 session 所有活跃 fact_block
    → 按 task_group_id 分组

  Step 2 · 逆向追溯来源 step（框架）
    → 对每个 fact_block，通过 sources 字段找到其来源 step_id
    → 从 step_summaries.jsonl 加载对应的结构化摘要

  Step 3 · 按需过滤（框架）
    → 根据当前任务查询（用户最新消息 / 全局压缩目标）提取 keywords
    → 仅保留 keywords 匹配的摘要（语义相关）
    → 排除 status: "negated" 或 fact_version: "deprecated" 的摘要

  Step 4 · 依赖链补全（框架）
    → 检查保留摘要的 depends_on 字段
    → 若依赖的 fact_block 存在但对应摘要未被选中 → 强制纳入
    → 若依赖缺失 → 触发局部重摘要（仅重处理缺失的 step 区间）

  Step 5 · 动态拼接（框架）
    → 按 created_at_step 升序排列
    → 拼接为：[{ref}] {summary} 格式
    → 注入 Slot 2 前端（head_buffer 之后）
```

**与缓存的关系**：组装产物注入位置固定在 skill_zone 之后，与 fact_block 注入区重合。只要 fact_block 不变，组装产物也不变 → prefix cache 命中。

### 15.6 与 Route 4 的关联

> Route 4（In-Context Learning as Meta-Learning）的核心命题：Transformer 的注意力机制本身就在做元学习——不需要更新权重，只在推理时通过上下文中的信息"学会"新任务。

本机制与 Route 4 的对应关系：

| Route 4 理论 | 本设计的工程落地 |
|-------------|---------------|
| ICL 是隐式梯度下降 | fact_block 是"梯度下降的产物"——从历史中提取的可迁移知识 |
| 上下文 = 训练数据 | fact_block 让上下文从"原始对话记录"升级为"结构化知识库" |
| 模型从 few-shot 示例中学习 | fact_block 本质是模型自己生成的 few-shot 示例（自举） |
| Scaling 本身在做元学习 | 压缩 + 结晶 = Scaling 过程中的"知识蒸馏" |

**一句话**：fact_block 机制是在工程层面实现"让模型从自己的历史中学习"——上下文不只是"给模型看的信息"，而是"模型从中学习的产物"。

### 15.7 风险与待定问题

| 风险 | 说明 | 缓解方案 |
|------|------|---------|
| fact_block 膨胀 | 大量 fact_block 占用上下文空间 | 预算上限（窗口 5%）+ 自动降级 |
| 事实提取质量 | 3B 模型可能提取出错误事实 | confidence 分级 + 全局审计 + 来源可追溯 + 事物质疑否定机制（§15.4.5.1） |
| 循环引用 | fact_block 引用自身来源的 step | 虚拟 step_id（负数）与正常 step_id 隔离 |
| prefix cache 失效 | fact_block 变化导致缓存失效 | fact_block 注入位置固定在 skill_zone 之后，变化时只影响该区域 |
| 与 task_group 归档的交互 | task_group 归档后，其 fact_block 如何处理 | fact_block 独立于 task_group 生命周期，按自身 ref_count 管理 |
| **摘要断裂**（v6 新增） | 跳过非重点 step 可能丢失隐性逻辑（如用户未明说的意图） | 摘要中强制保留 depends_on 依赖链；组装时发现依赖缺失 → 自动触发局部重摘要（仅重处理缺失的 step 区间） |
| **历史摘要过期**（v6 新增） | 早期摘要可能被后续事实推翻 | 摘要中记录 fact_version（如 fb_-1_v1）；归档时检查版本一致性，过期摘要自动标记 `status: "deprecated"`；事物质疑否定机制（§15.4.5.1）主动标记 `status: "negated"` |
| **检索效率**（v6 新增） | 海量摘要需快速匹配 | 轻量级索引方案：用 SQLite 存摘要元数据（step_id, keywords, session_id），无需 Redis；关键词预生成：摘要生成时自动提取技术术语（通过分词 + 项目术语表过滤） |

| 待定问题 | 说明 |
|---------|------|
